# Рабочий цикл агента

Подробная процедура к контракту [AGENTS.md](../../AGENTS.md). Отвечает на вопрос «в каком порядке
действовать», чтобы результат не требовал переделок. Устройство документации —
[doc-maintenance.md](doc-maintenance.md).

## Перед началом

1. **Сформулируй результат** одной фразой: изменённое поведение, новый файл, исправленный дефект,
   обновлённый документ.
2. **Прочитай минимум** по типу задачи:

   | Тип задачи | Что прочитать |
   | --- | --- |
   | Новая функциональность | `AGENTS.md` → `docs/architecture.md` → `docs/roadmap.md` → ADR |
   | Исправление дефекта | `AGENTS.md` → `architecture.md` § Инварианты → затронутый модуль |
   | Рефакторинг | `architecture.md` → ADR → тесты затронутой области |
   | Команды / сборка / инсталляторы | `development.md` → `project-map.md` § Сборка и артефакты |
   | Только документация | `docs/README.md` → `doc-maintenance.md` |
   | Новое решение / стек | `docs/adr/README.md` → `architecture.md` |

   Для изменений звука добавь в чтение `AGENTS.md` § Engine facts: измеренные законы
   оригинала — контракт, а не догадки; «улучшать» их без нового измерения нельзя.

3. **Проверь состояние**: `git status`; `python3 scripts/doc_system.py check` — не сломан ли
   репозиторий до тебя. Чужие незакоммиченные изменения не перезаписывай.
4. **Спланируй**: больше двух шагов — веди список; архитектурные развилки — ADR или вопрос
   пользователю до реализации.

## Цикл работы

```text
понять → сориентироваться → спланировать → изменить → проверить → задокументировать → отчитаться
```

1. **Понять** требование и текущее устройство (документация и код).
2. **Сориентироваться** в коде: сначала `architecture.md`/ADR, затем точечное чтение файлов;
   для больших репозиториев — семантический поиск, если он доступен.
3. **Спланировать** проверяемые шаги: для каждого — какой тест/проверка докажет, что он сделан.
4. **Изменить** минимальным диффом, соблюдая правила кода из `AGENTS.md`.
5. **Проверить** узко, затем полный шлюз. Соответствие проверки типу изменения:

   | Изменение | Обязательная проверка |
   | --- | --- |
   | Движок (`EngineCore/`) | `make -C EngineCoreTests test` + сравнение рендеров до/после: все фабричные, стартовые и библиотечные патчи (правило в `AGENTS.md`) |
   | Переносимые сервисы (`EditorCore/`) | `make -C EngineCoreTests test` (там же `SettingsTests`, `ThemesTests`, `ProgramChangeTests`, `UpdateCheckTests`) |
   | Чистая комната / новый замер | скрипт `tools/s1ref/measure_*.py` → `reference/meta/*.json` → `gen_tables.py`; таблицы руками не правим |
   | mac VST3 / AUv2 | `./build_vst3.sh`, затем `validator` (47/47, запускать с `HOME=$(mktemp -d)`) и `auval -v aumu OXS2 OXOM` |
   | iPad AUv3 | `xcodebuild … -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build` + `tools/au_harness` |
   | Windows | `build_windows.bat` (+ `--bench`), перед отправкой — `tools/win_check/check.sh` |
   | Документация | `python3 scripts/doc_system.py check` |

6. **Задокументировать**: документы по карте, `CHANGELOG.md` при пользовательском изменении,
   ADR при решении, `touch` для затронутых документов.
7. **Отчитаться** по шаблону ниже и записать состояние в [handoff.md](handoff.md).

Границы, которые нельзя переступать в цикле: не дизассемблировать и не декомпилировать
оригинал, не копировать его графику, не коммитить чужие банки патчей, не менять
`third_party/` (только строковые патчи по сгенерированным копиям в
`OxoSynth2VST3/CMakeLists.txt`).

## Проверка результата

| Что проверяем | Чем |
| --- | --- |
| Сборка и C++-тесты | `make -C EngineCoreTests test` |
| Звук против оригинала | сравнение рендеров (`tools/s1ref/compare.py`, `compare_sy1.py`) до/после изменения движка |
| Плагин в хосте | `validator` (47/47) и `auval -v aumu OXS2 OXOM`; iPad — `tools/au_harness` |
| Поведение | тесты проекта; запуск пользовательского сценария |
| Документация | `python3 scripts/doc_system.py check` (структура, ссылки, якоря, свежесть) |
| Актуальность | `python3 scripts/doc_system.py stale` |
| Чистота дерева | `git status`: без артефактов сборки и случайных файлов |

Если проверку выполнить нельзя — скажи это прямо и предложи, как проверить вручную. Запрещено
писать «тесты проходят», не запустив их.

## Обновление документации

1. Определи документы по карте в `AGENTS.md` § Документация.
2. Внеси правки: факты, команды, ссылки (не в генерируемых фрагментах).
3. Пользовательское изменение — `CHANGELOG.md` → `[Unreleased]`.
4. Отметь проверку: `python3 scripts/doc_system.py touch docs/architecture.md CHANGELOG.md`
   (или `make docs-touch ARGS="..."`).
5. `python3 scripts/doc_system.py check`. Новый документ — зарегистрируй в `docs/docs.toml`.

Отметка `touch` — утверждение «я прочитал документ и он соответствует коду». Отметка обновляет
момент проверки и снимает предупреждение ещё до коммита. Если в репозитории есть коммит, но база
проверки не зафиксирована — один раз выполни `touch --all` (baseline).

## Handoff

Каждая сессия заканчивается записью в [handoff.md](handoff.md), даже если работа не завершена.
Формат — в документе. После записи: `touch docs/agents/handoff.md`.

## Отчёт пользователю

```markdown
## Что сделано
- <изменение 1>
- <изменение 2>

## Чем проверено
- `make -C EngineCoreTests test` — зелёный
- `python3 scripts/doc_system.py check` — без ошибок
- <дополнительная проверка/запуск>

## Документация
- обновлены: <файлы>; проверка отмечена

## Риски и открытые вопросы
- <если есть; иначе — «нет»>

## Следующий шаг
- <что логично делать дальше>
```

Если задача провалена или частично выполнена — скажи прямо: причину, что сделано, варианты.
