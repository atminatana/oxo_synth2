# ADR-0001: Фиксируем архитектурные решения через ADR

## Статус

Accepted — 2026-11-12.

## Контекст

Проект развивается в сессиях ИИ-агентов: контекст между сессиями не сохраняется, а решения
(стек, границы модулей, форматы данных, процесс) влияют на код надолго. Без письменной фиксации
следующая сессия заново обсуждает те же развилки, а принятые компромиссы теряются. Комментарии в
коде объясняют «что», но не «почему рассматривали и отвергли альтернативу».

## Решение

Каждое существенное архитектурное решение фиксируется отдельным файлом
`docs/adr/NNNN-kebab-case-title.md` по шаблону из [README](README.md). Решение считается
принятым, когда ADR имеет статус `Accepted` (или пользователь явно согласовал его в задаче).
Принятые ADR не переписываются: изменение оформляется новым ADR, старый получает статус
`Superseded by ADR-NNNN`. ADR регистрируются в манифесте документации как `immutable`.

Значимые решения, требующие ADR: выбор стека и зависимостей, `unsafe`, форматы данных и
сохранений, публичное поведение/API, изменения процесса разработки (CI, хуки, документация).

## Альтернативы

- **Только переписка с пользователем.** Отвергнуто: не видна следующей сессии, не связана с
  кодом, теряется при смене инструмента.
- **Один большой `docs/decisions.md`.** Отвергнуто: конфликты при параллельных правках,
  невозможно помечать статусы независимо, история затирается.
- **Тяжёлый процесс (RFC, ревью-комитет).** Отвергнуто: непропорционально размеру проекта.

## Последствия

- Появляется явная история «почему» и меньше повторных обсуждений.
- Нужно поддерживать индекс ADR и статусы; номер выдаётся вручную.
- ADR обязаны быть в манифесте `docs/docs.toml`, иначе `check` не пропустит файл.
- Откат решения виден по цепочке `Superseded`, а не только по истории git.
