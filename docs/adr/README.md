# Architecture Decision Records (ADR)

ADR — короткие записи о принятых архитектурных решениях: контекст, решение, альтернативы и
последствия. Они объясняют **почему** код устроен так, и избавляют следующие сессии от повторного
обсуждения развилок.

## Процесс

1. Решение назрело, если оно меняет структуру/границы модулей, добавляет зависимость или
   `unsafe`, меняет публичное поведение, форматы данных или процесс разработки.
2. Скопируй шаблон (ниже) в `docs/adr/NNNN-kebab-case-title.md`, где `NNNN` — следующий номер.
3. Заполни разделы: статус, контекст, решение, альтернативы, последствия. Кратко: страница — уже
   много.
4. Добавь ссылку из затронутых документов и строку в индекс ниже.
5. `python3 scripts/doc_system.py touch docs/adr/README.md` и `check`.
6. Изменение принятого решения — **новый** ADR со статусом `Accepted`, старый помечается
   `Superseded by ADR-NNNN`. Существующие ADR не переписываются (они `immutable`).

## Статусы

| Статус | Значение |
| --- | --- |
| `Proposed` | предложено, ждёт решения |
| `Accepted` | принято и действует; код должен соответствовать |
| `Rejected` | отклонено; причина сохранена, чтобы не предлагать снова |
| `Superseded by ADR-NNNN` | заменено новым решением |
| `Amended by ADR-NNNN` | дополнено без отмены |

## Шаблон

```markdown
# ADR-NNNN: Краткое название решения

## Статус

Proposed | Accepted | Rejected | Superseded by ADR-NNNN — дата.

## Контекст

Какая проблема/сила требует решения. Факты, ограничения, требования. Без пересказа истории
проекта — только то, что влияет на выбор.

## Решение

Что решили и как применять: какие модули/инструменты/правила это затрагивает.

## Альтернативы

Что рассматривали и почему отвергли — самая ценная часть для будущих сессий.

## Последствия

Что станет проще, что сложнее, какие риски и что поддерживать. Включая цену отката.
```
